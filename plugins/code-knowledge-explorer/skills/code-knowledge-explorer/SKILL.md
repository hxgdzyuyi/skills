# 代码知识探索

当用户希望以学习为目的探索仓库或某个代码区域时使用本 skill。典型触发语包括：“我要探索代码的目标：...”、“带我探索这部分代码”、“我想理解这个模块/功能/调用链/数据流”等。

## 硬性规则

- 所有架构结论、题目和解释都必须基于本轮实际读过的仓库代码。不要编造目录、模块、函数、状态名或流程。
- 优先使用 `rg`、`rg --files`、`git grep`、包清单、路由/配置文件、测试文件和直接文件阅读来建立证据。
- 引用代码时尽量给出具体路径和行号。引用前使用 `nl -ba <file>` 或等价方式读取带行号内容。
- 如果探索目标过于模糊，先检查仓库结构并作出合理聚焦，在总结中明确写出“探索假设”。
- 输出文本尽量使用中文。代码标识符、命令、文件路径、API 字段名和协议字段可以保留原文。
- 选择题必须考架构理解、模块职责、调用关系、数据/状态流转或关键实现细节，不要考表层语法。
- 不要在用户提交前暴露正确答案。正确答案只能放入传给 `open_code_exploration_quiz` 的隐藏工具参数，不要写在可见聊天内容里。
- 选项长度必须刻意均衡。正确选项不能是四个选项中唯一最长的选项，也不能因为细节最多、限定语最多而显得明显更像正确答案。
- 每题四个选项应尽量使用相近句式和颗粒度；如果正确项需要更长表述，就压缩正确项或补足干扰项的信息密度。

## 工作流程

1. 理解探索目标。
   - 解析用户想了解的范围：目录、功能、模块、业务流程、技术问题或待解疑问。
   - 如果目标模糊，先扫描仓库并选择最合理的聚焦范围，同时把这个选择标为假设。

2. 自动探索代码库。
   - 找出相关目录和文件。
   - 阅读可能的入口、公开 API、路由/命令处理器、核心类/函数、数据模型、状态容器、测试和集成边界。
   - 顺着重要调用链、依赖关系和数据/状态流转继续追踪，直到足够解释设计。
   - 记录每个结论对应的代码证据。

3. 在聊天中生成结构化架构总结。
   视情况包含：
   - 探索假设
   - 相关目录与文件
   - 核心模块职责
   - 关键调用链
   - 重要数据结构或状态流转
   - 设计意图与潜在复杂点
   - 建议下一步阅读

4. 生成恰好五道单选题。
   每题必须包含：
   - 题干
   - 恰好 4 个选项
   - 唯一正确选项
   - 考察的知识点
   - 出题依据的代码路径和行号
   - 提交后用于判题的详细解释
   - 答错后需要补充理解的复习重点

5. 打开 MCP App 选择题界面。
   - 调用 MCP 工具 `open_code_exploration_quiz`，传入架构总结和五道题。
   - 正确答案、判题解释、复习重点只放在工具调用参数中。
   - 可见聊天里只说明“交互式测验已打开，请在界面中作答并提交”。

## 题目质量要求

- 正确答案位置要分散，不要固定为同一个字母。
- 不要使用“最长最详细的选项就是正确答案”的模式。
- 对每道题自检：计算四个选项的大致长度。如果正确选项是唯一最长选项，必须重写。
- 干扰项必须是基于代码上下文可能出现的误解，而不是明显荒谬或过短的占位句。
- 四个选项最好都围绕同一层级的概念，例如都描述模块职责、都描述调用链节点、或都描述状态流转结果。
- 题目和选项尽量使用中文；只有代码符号、路径、协议名、函数名等必要技术词保留原文。

## 降级处理

如果 MCP 工具不可用，仍然给出架构总结和五道题，但不要包含正确答案。请用户用选项字母回答，等用户回复后再判题并解释。
